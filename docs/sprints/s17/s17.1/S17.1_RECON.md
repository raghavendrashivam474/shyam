## 2. Interface Analysis & Signature Audits

### 2.1 S16 Continuity Service (`src/shyam/continuity/service.py`)
S16 coordinates the continuity pipeline via a 7-stage state machine:
`REQUESTED -> VALIDATING -> TARGET_SELECTED -> AUTHORIZED -> PREPARING -> TRANSFERRING -> RECONSTRUCTING -> CONTINUING -> VERIFYING -> COMPLETED`.

* **Boundary Execution Call:**
  `async def request_continuity(self, request: ContinuityRequest) -> ContinuitySession: ...`
* **Contract Model Dependencies:**
  * `ContinuityRequest`: Carries `work_id` (Zarya N2), `source_device_id` (S13), `portable_work` (Zarya N3 raw dict representation), `artifact_paths` (tuple of local paths), and `target_constraints` (S9).
  * `ContinuityTarget`: Carries `node_id` (S8/S9), `provider_id` (S9), and `device_id` (S13).

### 2.2 Zarya Provider Boundary (`src/shyam/providers/zarya/provider.py`)
* **Boundary Integration Call:**
  `def continue_work(self, portable_work: dict[str, Any], source_device_id: str = "", continuity_id: str = "") -> ContinuationResponse: ...`
* **Client Transport Class:** `ZaryaClient`
  * Hardcoded default base URL: `http://127.0.0.1:8765/ecosystem/v1`
  * Authentication: Injects `X-Ecosystem-Token` header.

### 2.3 Flux Provider Boundary (`src/shyam/providers/flux/provider.py`)
* **Boundary Integration Call:**
  `def transfer(self, peer_id: str, artifact_path: str, artifact_name: str | None = None, is_directory: bool = False) -> FluxTransferResponse: ...`
* **Client Transport Class:** `FluxClient`
  * Hardcoded default base URL: `http://127.0.0.1:9100/flux/v1`

## 3. Discovered Integration Gaps (The Real-World Friction)

The following three major friction points have been identified in the current code that must be handled when validating across two physical nodes:

### Gap A: The Zarya Routing Gap (No Target Parameter)
In `ContinuityService._continue_on_target()`, the coordination pipeline attempts to trigger continuation by calling:
`continuation_resp = await loop.run_in_executor(None, self._zarya.continue_work, req.portable_work, req.source_device_id, session.continuity_id)`
* **The Problem:** `self._zarya` represents Node A's local Zarya agent. The signature of `continue_work` does not accept a target destination node or peer ID.
* **Physical Consequence:** Node A's local Zarya provider receives the command but has no context specifying which remote Zarya instance (Node B) must perform the reconstruction and execution.
* **Validation Requirement:** Confirm whether Zarya N4 internally resolves the target node or if target execution requires dispatch via a target-specific provider client.

### Gap B: Node ID <-> Flux Peer ID Equivalence Assumption
In `ContinuityService._transfer_artifacts()`, the service delegates artifact transfer to Flux:
`self._flux.transfer(session.target.node_id, artifact_path)`
* **The Problem:** S16 assumes the S8/S9 `node_id` is identical to the Flux `peer_id`.
* **Physical Consequence:** If Shyam represents nodes using S13 UUIDs while Flux uses native Libp2p/Noise Peer IDs, the transfer invocation will fail to locate the target peer unless mapped properly.
* **Validation Requirement:** S8 Discovery Registry must verify mapping between a discovered node's S13 Node ID and its Flux Peer ID (stored in `DiscoveredProvider.metadata`).

### Gap C: Hardcoded Localhost Loopback Bindings
Both `ZaryaClient` and `FluxClient` default to loopback addresses (`127.0.0.1`).
* **The Policy:** Local provider boundaries must remain local (Node A talks to Local Zarya/Flux; Node B talks to Local Zarya/Flux).
* **Validation Requirement:** Cross-node transport is the responsibility of the underlying provider networks (Zarya EIP-1 mesh, Flux P2P network). S17.1 must validate these background transports.
