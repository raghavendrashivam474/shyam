## 1. WHAT EXISTS

### Runtime Lifecycle (src/shyam/core/runtime.py — 528 lines)
- ShyamRuntime has full async lifecycle: start() / stop() / __aenter__ / __aexit__
- LifecycleState enum: CREATED → INITIALIZING → RUNNING → STOPPING → STOPPED → ERROR
- start() initializes: identity, keypair, trust, sync, bootstrap, continuity, providers, discovery, context
- stop() tears down: context_service, provider_fabric, discovery
- State transitions are guarded by _lock and InvalidStateTransitionError

### Provider Contracts
- FluxProvider.refresh_status() → AvailabilityStatus (polls Flux gateway)
- ZaryaProvider.refresh_status() → AvailabilityStatus (polls Zarya agent)
- Both return UNAVAILABLE if not connected or on exception
- Both set _is_connected = False on failure
- connect() is called ONCE during runtime.start()

### AvailabilityStatus (src/shyam/capabilities/model.py)
- StrEnum: REGISTERED, AVAILABLE, UNAVAILABLE
- Used for capability availability, not component lifecycle

### EcosystemNodeState (src/shyam/discovery/ecosystem_models.py)
- StrEnum: KNOWN, AVAILABLE, UNAVAILABLE, STALE
- Used for remote discovered nodes, not local components

### Event Bus (31 existing event types)
- RuntimeStartedEvent, RuntimeStoppedEvent, RuntimeStoppingEvent, RuntimeErrorEvent
- ProviderRegisteredEvent, ProviderUpdatedEvent, ProviderUnregisteredEvent
- EcosystemNodeDiscoveredEvent, EcosystemNodeLostEvent, etc.
- No component readiness events exist yet

### Context Models (src/shyam/context/models.py)
- EcosystemContext: state, local_node_id, has_active_work, stale_node_ids
- EcosystemState: version, captured_at, discovery, active_work, recent_activity

### Settings (src/shyam/core/config.py)

- flux_enabled, flux_url
- discovery_enabled, discovery_port, discovery_interval, discovery_expiry

### CLI (src/shyam/cli.py)
- Entry point: shyam.cli:main (via pyproject.toml [project.scripts])
- Already does: async with runtime: + signal handling
- No changes needed for S17.5

## 2. THE GAP

Current startup behavior in runtime.start():

    connected = self.zarya_provider.connect()  # ONE SHOT
    if connected:
        # register provider + capabilities
    else:
        logger.info("Zarya not reachable. Continuing standalone.")
        # NEVER CHECKS AGAIN

Problems:
1. If Zarya/Flux starts 3 seconds after Shyam, Shyam never notices
2. If Zarya/Flux crashes and restarts, Shyam never recovers
3. No programmatic way to query "is the ecosystem ready?"
4. No events fired when component availability changes
5. No ecosystem readiness aggregation

## 3. WHAT S17.5 WILL ADD

### New Module: src/shyam/core/readiness.py
- ComponentState enum: UNKNOWN, STARTING, READY, UNAVAILABLE, FAILED
- EcosystemReadiness enum: STARTING, READY, DEGRADED, UNAVAILABLE
- ReadinessTracker class:
  - Async background task
  - Polls refresh_status() on configurable interval
  - Tracks component state transitions
  - Derives ecosystem readiness from component states
  - Publishes events on state changes
  - Clean start/stop lifecycle

### New Events (in src/shyam/events/bus.py or src/shyam/core/readiness.py)
- ComponentReadinessChangedEvent(component, old_state, new_state)
- EcosystemReadinessChangedEvent(old_readiness, new_readiness)

### New Setting
- readiness_poll_interval: float = 3.0 (seconds)

### Runtime Integration (src/shyam/core/runtime.py)
- Create ReadinessTracker in start() after provider connection attempts
- Start tracker as background asyncio task
- Stop tracker in stop()
- Expose readiness state via runtime property

### What S17.5 will NOT do
- No process supervision
- No spawning Zarya/Flux
- No second discovery system
- No UI/dashboard
- No architectural rewrites

## 5. RISK ASSESSMENT

| Risk | Mitigation |
|------|-----------|
| ReadinessTracker blocks runtime.start() | Run as background task, never block |
| Polling overwhelms providers | Default 3s interval, configurable |
| State inconsistency under concurrency | Use asyncio.Lock in tracker |
| refresh_status() side effects | Already tested in S17.4, idempotent |
| Test flakiness from timing | Use short intervals in tests, mock time |
