## 2. Resolution of the Three Transport Gaps

### Gap 1: Shyam Node ID ↔ Flux Peer ID Resolution
- **Problem in S17.1:** \ContinuityService._transfer_artifacts()\ passed the Shyam \
ode_id\ directly to \FluxProvider.transfer()\, failing because Flux requires a UUID-v4 \peer_id\.
- **Resolution in S17.2:**
  - Extended \ContinuityTarget\ model with optional \lux_peer_id: str | None\.
  - In \ContinuityService._select_target()\, extracted \lux_peer_id\ from the selected \NavigationCandidate.metadata\ (checking top-level, \
ode\, and \provider\ metadata blocks).
  - In \ContinuityService._transfer_artifacts()\, resolved destination via \session.target.flux_peer_id or session.target.node_id\.

### Gap 2: Zarya Cross-Node Routing
- **Problem in S17.1:** \ContinuityService._continue_on_target()\ invoked the local \ZaryaProvider\ instance (bound to \127.0.0.1:8765\) with no destination parameter.
- **Resolution in S17.2:**
  - Extended \ContinuityTarget\ model with optional \zarya_url: str | None\.
  - Extended \ZaryaProvider.continue_work()\ with optional \	arget_url: str | None = None\.
  - When \	arget_url\ is provided, \ZaryaProvider\ dynamically instantiates a target-addressed \ZaryaClient\ sharing the configured authorization token, leaving the local client state untouched.
  - \ContinuityService._continue_on_target()\ conditionally passes \session.target.zarya_url\ when present.

### Gap 3: Metadata Alignment Across Discovery & Navigation
- **Problem in S17.1:** Candidate metadata structure was nested under \merged_metadata = {"node": ..., "provider": ...}\ by \CandidateDiscoverer\.
- **Resolution in S17.2:**
  - \ContinuityService\ implements resilient metadata traversal across root, \provider\, and \
ode\ scopes to extract transport descriptors seamlessly.
