## 1. Current Shyam Provider Contract

### ContinuityService (src/shyam/continuity/service.py)

The S16 pipeline runs: VALIDATING -> TARGET_SELECTED -> AUTHORIZED ->
PREPARING -> TRANSFERRING -> RECONSTRUCTING -> CONTINUING -> VERIFYING.

**Transfer stage** (_transfer_artifacts):
- Calls self._flux.transfer(session.target.node_id, artifact_path)
- **BUG:** passes Shyam 
ode_id where Flux expects peer_id (UUID-v4)

**Continuation stage** (_continue_on_target):
- Calls self._zarya.continue_work(portable_work, source_device_id, continuity_id)
- **BUG:** self._zarya is always the LOCAL ZaryaProvider (127.0.0.1:8765)
- No mechanism to address a remote Zarya instance

### ContinuityTarget (src/shyam/continuity/models.py)

Current fields: 
ode_id, provider_id, device_id, 	rust_verified.
Missing: lux_peer_id, zarya_url (transport addresses).

## 2. Current Flux Transport Contract

### FluxClient (src/shyam/providers/flux/client.py)

- initiate_transfer(peer_id: str, artifact_path: str, ...) — requires Flux peer_id
- connect_peer(peer_id: str) — explicit connection step available
- get_peers() — returns FluxPeersResponse with all known peers
- get_peer(peer_id: str) — returns FluxPeerInfo with connectivity status

### FluxIdentityResponse

- peer_id: str — UUID-v4, the authoritative Flux identity

### Key insight

Flux already has full peer discovery and connectivity. The only gap is
that S16 does not resolve the Shyam node_id to the corresponding Flux
peer_id before calling transfer.

## 3. Current Zarya Transport Contract

### ZaryaClient (src/shyam/providers/zarya/client.py)

- continue_work(portable_work, source_device_id, continuity_id)
- POSTs to {base_url}/work/continue
- ase_url defaults to http://127.0.0.1:8765/ecosystem/v1
- **No target parameter** — the target is implicit in the base_url

### ZaryaProvider (src/shyam/providers/zarya/provider.py)

- Single-instance design: one provider = one Zarya daemon
- __init__ takes ase_url — so a remote Zarya needs a different URL
- continue_work() delegates to self._client.continue_work()

### Key insight

Zarya's transport is HTTP. Cross-node continuation requires a ZaryaClient
pointed at the remote node's Zarya URL. The URL must come from ecosystem
metadata.

## 4. Current Node Identity Relationship

### DiscoveredNode.metadata (src/shyam/discovery/ecosystem_models.py)

- metadata: dict[str, Any] — extensible, already used for transport info
- Can carry {"zarya_url": "http://<remote-ip>:8765/ecosystem/v1"}

### DiscoveredProvider.metadata

- metadata: dict[str, Any] — can carry {"flux_peer_id": "<uuid>"}

### NavigationCandidate.metadata

- "Merged metadata from node and provider for selection context"
- This is the bridge: S9 already merges metadata into the candidate
- S16 can extract transport addresses from selected.metadata

## 5. Required Changes (Minimal)

### A. ContinuityTarget model extension
- Add lux_peer_id: str | None field
- Add zarya_url: str | None field
- Both optional to preserve backward compatibility with existing tests

### B. _select_target() enhancement
- After S9 returns NavigationCandidate, extract lux_peer_id and
  zarya_url from selected.metadata
- Populate the new ContinuityTarget fields

### C. _transfer_artifacts() fix
- Use session.target.flux_peer_id instead of session.target.node_id
- Fall back to 
ode_id if lux_peer_id is None (local case)

### D. _continue_on_target() fix
- If session.target.zarya_url is set and differs from local:
  - Create a temporary ZaryaClient with the remote base_url
  - Call continue_work on that client
- If local (zarya_url is None or matches local): use existing self._zarya

### E. No architectural changes needed
- S8 metadata already supports arbitrary key-value pairs
- S9 already merges metadata into NavigationCandidate
- S13 trust is unchanged
- Flux and Zarya client contracts are unchanged
- No new subsystems required

## 6. Potential Architectural Impact

**None.** All changes are additive fields and routing logic within the
existing S16 pipeline. No ADR required unless the metadata approach
proves insufficient during integration testing.
