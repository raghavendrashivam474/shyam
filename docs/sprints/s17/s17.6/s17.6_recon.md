## 1. Objective

Create the thinnest possible human-facing layer over the existing Shyam runtime
so a person can express a natural-language intent, see ecosystem readiness,
trigger an already-proven capability (cross-device continuity), and receive a
human-readable result — without exposing Zarya, Flux, or internal routing.

## 2. Pre-Existing Architecture Inventory

### Runtime (`src/shyam/core/runtime.py`)
- `ShyamRuntime` — async context manager, single entry point.
- `.readiness` → `EcosystemReadiness` (property, delegates to tracker).
- `.get_readiness_snapshot()` → `EcosystemReadinessSnapshot`.
- `.navigate(NavigationRequest)` → `NavigationResult`.
- `.invoke_composite(...)` / `.run_workflow(...)`.
- `.get_ecosystem_context()` / `.get_ecosystem_state()`.
- `.events` → `EventBus` (publish/subscribe).
- `.continuity_service` → `ContinuityService` (initialised in `start()`).
- `.identity_manager` → `IdentityManager` (provides `node_id`).

### Readiness (`src/shyam/core/readiness.py`)
- `ReadinessTracker` with async background polling.
- `ComponentState`: STARTING | READY | DEGRADED | UNAVAILABLE | FAILED.
- `EcosystemReadiness`: STARTING | READY | DEGRADED | UNAVAILABLE.
- Events: `ComponentReadinessChangedEvent`, `EcosystemReadinessChangedEvent`.
- `readiness` is a read-only `@property` returning `self._readiness`.

### Continuity (`src/shyam/continuity/service.py`)
- `ContinuityService.request_continuity(ContinuityRequest)` → `ContinuityResult`.
- Internal pipeline: validate → select_target → verify_trust →
  prepare_artifacts → transfer_artifacts → continue_on_target → verify_result.
- `ContinuityRequest` fields: `work_id`, `source_device_id`, `portable_work`,
  `artifact_paths`, `target_constraints`, `continuity_intent`.
- `ContinuityOutcome`: SUCCESS | FAILED | CANCELLED | UNSUPPORTED | UNKNOWN.

### Navigation (`src/shyam/navigation/navigator.py`)
- `HybridNavigator.navigate(NavigationRequest)` → `NavigationResult`.
- Target selection is fully internal; surface must NOT select devices.

### Events (`src/shyam/core/events.py` via runtime)
- `EventBus` with `publish()` / `subscribe()` pattern.
- No polling needed; surface subscribes to readiness events.

### CLI (`src/shyam/cli.py`)
- Existing `run_runtime()` with graceful shutdown.
- Existing `main()` entry point via `python -m shyam`.
- No interactive mode or surface integration prior to S17.6.

## 4. Architectural Boundaries

### Surface OWNS:
- Input normalisation (text/voice → `InteractionRequest`)
- Intent parsing (`InteractionRequest` → `UserIntent`)
- Human-readable presentation (`ContinuityResult` → plain text)
- Transient UI state tracking

### Surface DOES NOT OWN:
- Target device selection
- Trust or identity management
- Workflow execution
- Continuity pipeline internals
- Artifact transfer
- Zarya or Flux invocation
- Ecosystem state management

### Key Constraint:
`readiness` is a read-only property. Tests must set
`runtime.readiness_tracker._readiness` directly rather than using
`unittest.mock.patch.object` on the property.

## 5. First Vertical Slice

**"Continue this work on my other laptop."**

```text
Human → Surface → IntentParser → CONTINUE_WORK
→ SurfaceCoordinator → ContinuityService.request_continuity()
→ S9 Navigator → Flux → Remote Zarya → Verification
→ Presenter → "Done — work continued on your other laptop."
```

## 6. Risk Register

| Risk | Mitigation |
|------|-----------|
| Over-engineering intent parsing | Deterministic keyword matching only; no LLM |
| Duplicating readiness system | Subscribe to existing events only |
| Leaking internal errors to user | Presenter translates; detail preserved in logs |
| Breaking existing CLI | New flags are additive; default behaviour unchanged |
| Voice dependency bloat | VoiceInputAdapter uses STT hook; no heavy deps |
